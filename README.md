# AI Gantt Planner

AI Gantt Planner — интерактивный планировщик проекта: пользователь загружает
задачи из Excel, просматривает их на диаграмме Гантта и меняет план через
AI-помощника на естественном языке. Формальные решения о датах, зависимостях и
целостности плана всегда проверяет Python backend по заданным правилам.

**Развёрнутое приложение:**
[https://bbaqdcimsde8vli202gq.containers.yandexcloud.net/](https://bbaqdcimsde8vli202gq.containers.yandexcloud.net/)

Основные возможности:

- готовый демонстрационный план сразу после открытия;
- интерактивная диаграмма Гантта с навигацией, выбором задач и предварительным
  просмотром изменений перед применением;
- импорт `.xlsx` с заменой или дополнением текущего плана и экспорт актуального
  плана в Excel;
- AI-команды для массового переноса, зависимостей, создания задач и назначения
  исполнителей;
- показ всех связанных задач, которые придётся сдвинуть, до применения
  изменений;
- карточка с информацией о задаче и сохранение текущего плана в браузере.

Стек: React, TypeScript, Vite, Frappe Gantt, Python, FastAPI, официальный MCP
Python SDK, OpenAI-compatible Responses API и Qwen в Yandex AI Studio.
Приложение поставляется одним Docker-образом и работает в Yandex Serverless
Containers.

## Локальный запуск

Требования: Python 3.12+, Node.js 20.19+ и npm. Для AI-запросов также нужна
локальная конфигурация Yandex AI Studio; без неё все детерминированные функции
планировщика остаются доступны.

Backend:

```powershell
cd backend
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev]"
.venv\Scripts\python -m uvicorn app.main:app --reload --env-file ..\.env
```

Frontend во втором терминале:

```powershell
cd frontend
npm install
npm run dev
```

Откройте `http://127.0.0.1:5173`. Vite проксирует `/api` на FastAPI по адресу
`http://127.0.0.1:8000`.

Для работы с реальным AI скопируйте `.env.example` в локальный `.env` и
заполните значения:

```text
YANDEX_CLOUD_API_KEY=<service-account API key>
YANDEX_CLOUD_FOLDER_ID=<AI Studio folder ID>
AI_MODEL=gpt://<folder ID>/qwen3.6-35b-a3b
AI_BASE_URL=https://ai.api.cloud.yandex.net/v1
```

`.env` игнорируется Git. API-ключ используется только backend-процессом и не
попадает во frontend, `localStorage` или Docker build arguments.

## Архитектура и ключевые решения

В MVP текущий план хранится в `localStorage` браузера. Backend получает
актуальный план с каждым запросом, проверяет или изменяет его и возвращает
обратно, но не хранит пользовательский план между запросами. FastAPI обслуживает
интерфейс и `/api` по одному адресу в production. Полная схема и границы
компонентов описаны в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Ключевые решения MVP:

- понедельник–пятница — рабочие дни; праздники не учитываются;
- поддерживается только зависимость Finish-to-Start: следующая задача может
  начаться после завершения предыдущей;
- backend отклоняет неизвестные задачи-предшественники, ссылку задачи на саму
  себя и циклы в зависимостях;
- если одна команда меняет несколько задач, backend сначала рассчитывает
  итоговый план целиком и только затем проверяет его на ошибки и конфликты;
- связанные переносы других задач показываются пользователю до применения;
- пока пользователь рассматривает предварительный просмотр, другие изменения
  плана временно недоступны. Сначала нужно применить или отменить текущие
  изменения либо восстановить демо, иначе просмотр может перестать
  соответствовать плану, для которого он был рассчитан;
- план хранится только в текущем браузере: общего или межустройственного
  хранилища в MVP нет;
- Frappe Gantt отвечает за отображение диаграммы и взаимодействие с ней. Правила
  рабочих дней, дат и зависимостей рассчитывает Python backend.

### Детерминированный backend и LLM

| AI понимает пользователя | Backend проверяет правила |
| --- | --- |
| что пользователь хочет изменить | допустимы ли новые даты |
| какие задачи он имеет в виду | не появились ли циклы в зависимостях |
| какое действие нужно подготовить | корректен ли Excel |
| когда нужно задать уточняющий вопрос | какие ещё задачи затронет изменение |
| как объяснить результат пользователю | можно ли безопасно применить итоговый план |

AI интерпретирует намерение пользователя, но не решает самостоятельно, какие
даты и зависимости допустимы. Финальную проверку всегда выполняет backend. При
неоднозначности AI задаёт уточняющий вопрос, а перенос связанных задач требует
решения пользователя.

### Реальное использование MCP

Для каждого запроса FastAPI делает переданный план доступным MCP-серверу. Модель
читает нужные задачи через инструменты `get_tasks`, `get_task` и
`get_dependencies`, а отдельные MCP-инструменты только подготавливают изменения.
Они не сохраняют план и не могут обойти проверку backend. Полный план напрямую
в запрос модели не вкладывается.

## Формат Excel

Принимается только `.xlsx`; обрабатывается только активный лист. Обязательные
колонки:

```text
задача
описание
исполнитель
длительность
предшественники
```

Заголовки нормализуются по регистру и пробелам. Неизвестные колонки и полностью
пустые строки игнорируются. Несколько предшественников разделяются `;`; поэтому
этот символ запрещён в названии задачи — способ экранирования в MVP не
предусмотрен.

Replace заменяет текущий план и детерминированно генерирует `TASK-001`,
`TASK-002`, ... в порядке строк. Append объединяет названия существующих и новых
задач, сохраняет существующие ID и начинает новые ID после максимального
`TASK-NNN`. Импорт выполняется целиком: при ошибке не применяется ничего.

[`sample/sample_tasks.xlsx`](sample/sample_tasks.xlsx) содержит параллельные
ветки и задачу с двумя предшественниками. Файл проходит обычный Replace import,
который доступен пользователю в приложении.

## Production container и deployment

Root `Dockerfile` собирает React через Vite, устанавливает Python runtime
dependencies и запускает FastAPI/Uvicorn от non-root пользователя. Локальный
production build:

```powershell
docker build --platform linux/amd64 --provenance=false --sbom=false `
  --tag ai-gantt-planner:local .
docker run --rm --publish 8080:8080 --env PORT=8080 ai-gantt-planner:local
```

Откройте `http://127.0.0.1:8080`. Повторяемый smoke:

```powershell
pwsh -File .\infra\docker\smoke.ps1
```

Delivery flow: immutable Git-SHA image → Yandex Container Registry → Yandex
Serverless Containers. Runtime credential передаётся из Yandex Lockbox только в
environment контейнера. Automation имеет read-only plan по умолчанию; подробная
инструкция находится в [`infra/yandex/README.md`](infra/yandex/README.md).

## Известные ограничения MVP

- план и контекст текущего AI-диалога хранятся только в `localStorage` конкретного
  браузера;
- нет пользователей, авторизации, отдельных рабочих пространств, истории и
  защиты от одновременного редактирования;
- нет календаря праздников, вех, учёта загрузки исполнителей и зависимостей
  SS/FF/SF;
- карточка задачи доступна только для чтения;
- повторный импорт экспортированного файла создаёт новые TASK-ID и заново
  рассчитывает расписание по обычным правилам импорта;
- публичное демо не требует авторизации и не предназначено для хранения
  конфиденциальных планов;
- нет автоматического переключения между AI-провайдерами, промышленного
  мониторинга и ограничений стоимости или частоты запросов.

Это сознательные ограничения тестового MVP, а не обещание полной production-
готовности. Порядок их закрытия описан в
[`docs/ROADMAP_TO_PRODUCTION.md`](docs/ROADMAP_TO_PRODUCTION.md).

## Использование AI-ассистентов при разработке

AI-ассистенты использовались для реализации отдельных компонентов, подготовки
базовой структуры, проверки кода, тестов и документации. Архитектура,
бизнес-правила, системная модель и границы MVP были определены и зафиксированы до
основной реализации.

Финальное поведение проверено автоматическими модульными, интеграционными и E2E-
тестами, а также вручную, включая развёрнутое приложение с настоящим Qwen.
Проект не позиционируется как автономно сгенерированный AI без инженерного
контроля.

Если разбить поэтапно всю работу:
1) Создание мастер чата для анализа задания, выявления недостающих требований. Описание ограничений, корректировка требований, выбор стека и технологий.
2) Планирование итераций, handoff и требуемых агентов.
3) Создание репозитория и его структуры.
4) Создание и заполнение AGENTS.MD и Brief
5) Передача задачи агенту Codex
6) Приемка задачи
7) Цикл передачи и приемок задач до удволитворительного результата
8) Загрузка приложения и создание окружения в яндекс консоли через CLI при помощи агента.
9) Оформление итоговой документации С ИИ, аудит с агентом Work, самостоятельные правки
10) Запись демо
11) Отправка тестового
